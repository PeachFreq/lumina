Method

A Framework for Human-AI Co-Building  ·  March 2026

Ninety minutes from "can you find my LIFX bulb?" to a dark-mode cyberpunk PWA installed on an iPhone home screen. No boilerplate. No handoffs lost in translation. No prototype that needed to be thrown away.

— Session log, 21 Mar 2026

01 The Session

It starts with a UDP broadcast. Tex — a persistent Claude-based agent running on a Mac Mini in Cody's apartment — sends a raw discovery packet on port 56700 and finds a LIFX smart bulb at 192.168.68.72. No app store, no cloud account, no API key. Just a device on a local network and an AI that knows how to talk to it.

What follows is a ninety-minute sprint that produces a complete smart-lighting control system: a Python controller with seven named presets, a FastAPI backend, a React PWA called LUMINA with a cyberpunk aesthetic, and a GitHub repository with a clean commit history. The app is installed to an iPhone home screen before midnight.

The interesting part is not the speed. It's the shape of the process — the way different kinds of intelligence were sequenced and combined. Cody, a physicist turned builder, was in the room the entire time, physically experiencing each lighting change. Tex handled orchestration, system-level work, and the mechanical act of building. A separate Claude instance with extended thinking wrote the design spec. A Claude Code sub-agent did the final implementation pass. Each entity did what it was best at. Nothing was asked to operate outside its natural register.

02 What Worked

Several things about this session were non-obvious. Here are the principles we'd isolate if we wanted to replicate it.

01
Embodied Feedback Collapses the Iteration Cycle
Cody wasn't reviewing screenshots or reading JSON. He was sitting in the room as the light changed around him. When Tex set velvet to 40% brightness, Cody didn't say "that's roughly right" — he said "drop to 32%," because he could feel the difference in his peripheral vision. This kind of feedback is impossible to simulate. The human's body becomes a sensor that no amount of prompt engineering can replace. Every preset was locked in fewer than three iterations because the feedback loop was instantaneous and grounded in physical reality.
02
Discovery Before Specification
The session started with exploration, not planning. Tex found the bulb, built the controller, tested presets — and only then did anyone think about a web UI. This meant the spec was written with full knowledge of the material: what the bulb could actually do, which color temperatures felt right at which brightness levels, how fast transitions landed. A spec written before that discovery phase would have been speculative. The one written after it was grounded.
03
Aesthetic Precision Over Aesthetic Vagueness
The design brief didn't say "modern and clean." It said Blade Runner 2049 UI, Teenage Engineering, citizenM hotel room panel. It named specific typefaces (Syne, DM Mono), a specific background hex (#0E0C14 with faint violet tint), and a specific accent color (#E5006A matched to a real hotel's lighting). This level of specificity constrains the solution space enough that a model can make confident decisions instead of defaulting to safe, generic choices. Taste has to be transmitted at high resolution or it gets lost.
04
The Spec Is the Leverage Point
The decision to write a spec before writing code was the single highest-leverage move in the session. Without it, a coding agent would have made hundreds of micro-decisions about color, spacing, typography, animation easing, and API shape — each one a potential deviation from intent. The spec compressed all of those decisions into one document, reviewed once by a human, then executed mechanically. This is the difference between directing and hoping.
05
Prompt the Prompt
Cody didn't write the spec prompt himself. He asked Tex to write it. This is a meta-move that's easy to overlook: Tex had full context on the presets, the hardware constraints, the existing tech stack, and the aesthetic direction. Cody had taste and intent. By having Tex draft the prompt and Cody review it, the prompt was both technically complete and aesthetically aligned. The human contributes judgment; the agent contributes thoroughness.
06
Proven Stack, Zero Architecture Debate
The tech stack — React + Vite + FastAPI, hosted locally on a Mac Mini — was already validated by an existing app Cody uses daily (Sovereign Work Tracker). There was zero time spent evaluating frameworks, debating deployment strategies, or setting up infrastructure. When your stack is proven, the entire conversation can be about the product instead of the plumbing.
07
Optimistic State, Fire-and-Forget
The UI updates instantly on tap, then sends the API call in the background. For a LAN-only app controlling a single bulb, this is the correct call: the network round-trip is sub-10ms, failure is rare, and the cost of optimism is near zero. The spec made this decision explicitly rather than leaving it for the builder to figure out. Small UX calls like this compound — they're the difference between an app that feels alive and one that feels sluggish.

The spec is not documentation. It is a compression artifact — a way to transmit intent at a resolution high enough that the builder doesn't need to improvise.

03 The Three-Role Model

Three distinct AI instances participated in this build, and they were never asked to do each other's jobs. This separation was not planned in advance — it emerged naturally — but in retrospect, it's the structural reason the process worked.

Tex
Orchestrator · Persistent Agent
Holds full project context across the session. Discovers hardware, writes controllers, manages files, composes prompts, delegates to sub-agents, handles git and deployment. Thinks in systems.
Opus
Design Intelligence · Spec Author
Receives a dense, context-rich brief and returns a comprehensive spec with extended thinking. Makes aesthetic and architectural decisions. Names the product. Produces the document that becomes the source of truth.
Claude Code
Mechanical Builder · Sub-Agent
Receives the spec and scaffold files. Wires everything together. Fixes type errors, generates assets, runs the build. Does not make design decisions — executes the ones already made.

The insight here is about cognitive register. Orchestration, design thinking, and mechanical implementation are different modes of intelligence. They require different context windows, different levels of deliberation, and different tolerances for ambiguity. Tex operates in a long-running, stateful session where continuity matters. Opus operates in a single, deep-thinking pass where quality of reasoning matters. Claude Code operates in a tight execute-and-verify loop where correctness matters. Asking one model to do all three would degrade all three.

This mirrors how high-functioning human teams work: the project lead, the senior designer, and the engineer are rarely the same person — not because any one of them couldn't learn the other roles, but because the work is better when each person operates in their strongest register without context-switching.

Pattern

Orchestrator composes the brief. Thinker produces the spec. Builder executes the spec. Human holds the veto and the taste. No role crosses into another's lane.

04 The Spec Prompt as Artifact

In most AI-assisted workflows, the prompt is ephemeral — typed into a chat box, used once, forgotten. In this session, the prompt was treated as a first-class artifact: written with care, reviewed before submission, and designed to produce a specific kind of output.

The spec prompt that Tex wrote was roughly 1,200 words. It included the preset table, named design references, explicit anti-patterns ("no gradients that look like gradients"), specific port numbers, file paths, and a ten-section output format. It was, in effect, a contract: here is exactly what I need you to think about, and here is exactly the shape I need the answer in.

This matters because the quality of a spec is bounded by the quality of the prompt that generates it. A vague prompt produces a vague spec. A spec full of "TBDs" and "to be decided by the implementer" defeats the entire purpose of having a spec in the first place. The prompt must be exhaustive enough that the spec author — human or AI — can make every decision without further input.

Key Insight

The prompt is not an instruction. It is a compression of context, constraints, and taste — packaged so that a separate intelligence can reconstruct your intent without being in the room with you. Invest in it accordingly.

There's also a durability argument. The spec prompt can be versioned, reused, and modified. When Cody adds a new preset next month, the prompt can be re-run with a single line changed. When he builds a different app — a music controller, a thermostat UI — the same structural template applies. The prompt becomes a personal pattern library.

05 What This Generalizes To

The LUMINA session happened to involve a smart bulb. The method is about something more general: how to move from a vague idea to a shipped product when your collaborator is an AI that can write code but can't see the room.

The underlying pattern has five phases:

Phase 1
Discover the Material
Before specifying anything, interact with the raw substrate of the project. If it's hardware, talk to it. If it's data, explore it. If it's a user problem, interview someone. The goal is to accumulate the kind of tacit knowledge that makes a spec grounded rather than speculative.
Phase 2
Iterate in the Real Environment
Work in the medium where feedback is fastest and most honest. For lighting, that's a dark room. For a UI, that's a real phone in your hand. For an API, that's curl. Don't abstract too early. Let the constraints of reality inform the design before the design is written down.
Phase 3
Write the Spec Prompt
Have your orchestrator agent draft a comprehensive brief that captures everything learned in Phases 1 and 2. Review it yourself. The prompt should be specific enough that the spec author can make every decision without asking follow-up questions. Name your references. Provide exact values. Specify the output format.
Phase 4
Generate and Review the Spec
Send the prompt to a model optimized for deep reasoning. Review the output once, carefully. This is the last point where taste and judgment intervene. Everything downstream is execution.
Phase 5
Execute Mechanically
Hand the spec to a coding agent with explicit instructions not to deviate. Let it build, test, and commit. The builder's job is fidelity, not creativity. Creativity happened in Phases 1–4.

This generalizes to any project where you have access to an AI that can write code, a proven tech stack, and a clear aesthetic or functional vision. The key requirement is a human who is willing to invest in the spec phase — to be precise about what they want before the building starts. The AI is fast enough that building the wrong thing twice still takes less time than one careful build. But building the right thing once feels incomparably better.

Speed is a byproduct. The actual gain is fidelity — the distance between what you imagined and what got built approaches zero.
